# Backend read latency on Dev, November 2026: what is slow and what changed

- [ ] `p2` - **ID**: `cpt-studio-design-perf-2026-11`

A measurement of the Dev backend's slowest routes, taken on 2026-11-11, and
the code changes made for the ones that are still slow in the code on
`AndrejK666/frontx-portal`. Dev ran an older build at the time
(2026-11-10, before the #1041 cold-read fixes), so some of what is slow on Dev
is already fixed in the branch. This document says which.

## How it was measured

- Latency per route: `http_server_request_duration_seconds` from
  VictoriaMetrics, by `http_route`, label `env="dev"`. The method is in
  `studio-backend/AGENTS.md` under "Finding what is slow". p50, p95 and p99
  come from `histogram_quantile` over the window. The total is the
  `increase` of `_sum`. The highest bucket is 10 s, so `10.00` means
  "10 s or more".
- Time of day: the same series by hour (`increase(...[1h])`), with the
  requests over 5 s counted from the `le="5"` bucket.
- Steady-state timings: `duration_ms` from the backend's access log. The pod's
  log keeps only the last few hours.

## Why they were slow

**A burst queued behind the domain model's pool.** With
`storage.artifacts: model` every artifact read (`/nodes`, `/activity`,
`/spec-rows`' files and findings, the counts) is a query to the domain
model's read model, and the documents gear's tables are kept there as well.
On the Dev build that pool had two connections, with
`acquire_timeout: 10s`. A project screen asks a dozen such reads at once, so
in a burst each one waited for a connection. That is why the p50 of `/activity`
is pinned at the 10 s bucket. The branch already has six connections
(#1041, `3314392f`), the tenant-chain cache (`e582afa2`) and the single-flight
read of a project's sources (`2a092263`). Those fix the burst. They do not
fix the next point.

**A page read the whole scope.** In model storage,
`ModelGraph::page` asked the model for every object of each listed type in
the scope (every file of a project, thousands of them) and then sorted and
sliced 50 of them in process. `count_in_scope` read every object to call
`len()` on the list. Without a type, `/nodes` asked for four types one after
another, each with its own access check and its own query. That gives the
steady 1.2–1.5 s, compared with about 0.12 s for one type.

**Independent reads waited for each other.** `/activity` read findings,
then comments, then the bindings' names. `/spec-rows` read bindings, then
documents, then the decisions. `/documents` checked the workspace and then the
project.

## What changed

- `ModelGraph::page` (`studio-backend/src/artifact_ingest/model_store.rs`)
  hands the page to the model: `where` (scope, and `repo` when given),
  `order_by` (`updated_at` descending when the listing sorts by date),
  `offset` and `limit`. The read model answers with one indexed SQL page and a
  count, so a page of 50 reads 50 rows. Over several types, each type returns
  the first `offset + limit` of its rows and the page is cut from their merge.
  The order and the total are those of `page_of_nodes`, and a test compares
  the two over every combination of type, repository, order, offset and
  limit. Pages that filter by `subject` or by text, and pages after a cursor,
  are still cut in process, because the model's types do not have those fields.
  A model that rejects the query, for example one whose type lacks
  `updated_at`, falls back to the old read and logs a warning.
- `count_in_scope` asks for one row per type and reads the model's `total`.
- One query per type runs concurrently (`query_types`). This covers every
  `list_in_scope` and the four-type listing.
- `run_bulk` (`studio-backend/src/domain_model/query.rs`) keeps its graph scan
  bound at `BULK_LIMIT` whatever page a gear asks for. Before this, a gear's
  page of 50 on a tenant whose read model was not filled yet would have scanned
  only `SCAN_LIMIT` objects, and its order and total would have been partial.
- `/activity` reads findings, comments and the bindings' names concurrently.
  `/spec-rows` does the same for bindings, documents and decisions, and
  `/documents` does it for its two tenant checks. The page is still read only
  after both checks pass.

Expected effect: `/nodes` without a type goes from four sequential
whole-scope reads to four concurrent page reads. That brings it close to the
one-type figure, about 0.1–0.2 s instead of 1.2–1.5 s. A page of the Files
tab no longer grows with the number of files in the project. In a burst, each
request holds the domain model's connections for a shorter time, which helps
the other requests in the same burst.

## What was not changed

- `/studio-connector/v1/connections` (1.7–2.2 s steady). Each request logs
  that 55 types "keep the schema they were registered with". That is the domain
  model checking gear declarations against a model that needs a type
  migration. The fix belongs to the type migration, not to the connector.
- `/studio-spec-mapping/v1/plan` and `/findings`, `/product/preview`, and the
  `project-domain-model` family. These run on a project's sources and
  documents, which the #1041 fixes already single-flight and bound. Measure
  them again on Dev once the branch is deployed, before changing them.
- `/studio-documents/v1/review-requests`: p50 is 30 ms. It was slow only in
  the burst.
- The graph-storage side (`$filter`, `count_nodes`) is separate work and is
  not touched here.

## How to check the result

After the branch is deployed to Dev, run the same queries over a window that
starts after the deploy, and compare `duration_ms` for
`/nodes?scope=…&limit=…` with the table above. A `/nodes` without a type
that still takes over a second, or a log line "the model could not cut the
page", means the page fell back to the old read.
